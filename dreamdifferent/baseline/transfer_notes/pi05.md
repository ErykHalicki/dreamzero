
For the model to receive a natural language prompt like `"bag the groceries"`, the LeRobot/GEAR dataset metadata must map task index 0 to that string, likely via:

```text
meta/tasks.jsonl

```

Expected good case:

```json

```

Potential bad case:


If the mapping is bad or missing, the model may be trained with `"0"` or an invalid language prompt instead of `"bag the groceries"`.

## pi0.5 transfer requirements

Do **not** blindly pass the same data into pi0.5 without matching the representation.

Need to align:

1. **Action dimension**
   - Current data: `action_dim = 48`
   - pi0.5 config should use `action_dim=48` unless slicing to a smaller control representation.

2. **State dimension**
   - Current data: `state_dim = 48`
   - pi0.5 data transform should pass the same 48D state if this is the intended control state.

3. **Action representation**
   - Need to confirm whether `action` is already relative delta or absolute target.
   - Dataset/config name `franka_relative` suggests relative representation, but this must be verified.
   - Avoid double-relative conversion in pi0.5.

4. **Temporal frequency and horizon**
   - Dataset appears to be ~50Hz.
   - DreamZero uses `action_horizon=24`, i.e. ~0.48 sec.
   - For a first comparable pi0.5 run, consider `action_horizon=24` unless using a pi0.5 checkpoint/config that strongly expects another horizon.

5. **Normalization**
   - Recompute pi0.5/OpenPI normalization stats after final data transforms.
   - If actions are relative, stats must be computed on relative actions.
   - If actions are absolute then converted to relative by the pipeline, stats must be computed after that conversion.

3. Numerically compare state/action:

Because `state` and `action` are both 48D, compare whether `action[t]` is closer to:

```text

```

If `action[t]` is much closer to `state[t+1] - state[t]`, then it is likely relative.
If `action[t]` is much closer to `state[t+1]` or `state[t]`, then it is likely absolute.

Need to be careful for hand/gripper dimensions and scaling; inspect per-dimension errors rather than only one global mean.

### What the code does for relative actions

`franka_relative.yaml` sets:

```yaml
relative_action: true
relative_action_per_horizon: false
relative_action_keys:
  - left_arm_joint_position
  - left_hand_joint_position
  - right_arm_joint_position
  - right_hand_joint_position
single_dataset_cls: groot.vla.data.dataset.lerobot_sharded.ShardedLeRobotSubLangSingleActionChunkDatasetDROID
```

Therefore DreamZero explicitly enables relative action conversion for all four Franka/ORCA action groups.

The sharded dataset class converts actions on the fly in `groot/vla/data/dataset/lerobot_sharded.py`:

```python
should_convert_to_relative = (
    (self.relative_action or self.relative_action_per_horizon)
    and len(sampled_indices) > 0
    and (self.relative_action_keys is None or subkey in self.relative_action_keys)
)
if should_convert_to_relative:
    action_data = self._convert_to_relative_action(...)
```

The conversion is:

```python
relative_action_data[chunk_start:chunk_end] = (
    action_data[chunk_start:chunk_end] - reference_state
)
```

where `reference_state` is the state at the chunk anchor index, using the corresponding state subkey.

So the important conclusion is:

```text
Raw parquet `action` is treated as absolute target/action.
DreamZero converts it to relative action during dataloading by subtracting the anchor state.
```

This means pi0.5/OpenPI should not blindly use the raw parquet `action` as the final action target if the goal is to match DreamZero. It should either:

1. implement the same transform: `relative_action[t+h] = raw_action[t+h] - state[t]`, per 24-step chunk and per matching state/action subkey; or
2. deliberately train pi0.5 on absolute actions, but then it is not directly matching DreamZero's relative-action setup.

## Eval / inference implication for relative action output

During training, DreamZero's dataloader turns absolute raw action chunks into relative targets:

```text
anchor = t
reference_state = state[t]
for h in 0..23:
    target_relative[h] = raw_action_absolute[t+h] - reference_state
```

This means the model learns to output a delta-from-current-anchor-state action chunk.

At eval/inference time, the reverse conversion must happen before sending commands to the robot if the robot controller expects absolute joint/hand targets:

```text
current_state = observed state at rollout time
pred_relative[h] = model output after denormalization
absolute_command[h] = pred_relative[h] + current_state
```

Usually the model/data pipeline handles normalization inversion, but the controller wrapper or eval policy must also add the current state back for relative-action dimensions. If that reverse step is missing, the robot would receive small deltas as if they were absolute joint targets, which would be wrong.

For pi0.5/OpenPI, to match DreamZero, implement the same convention:

- training target: `raw_action[t:t+24] - state[t]`
- inference postprocess: `predicted_relative_action + current_state`
- compute normalization statistics on the relative targets, not raw absolute action
